Why it matters

  • Money logic is pure. Every rate, tax, allocation and rounding decision is plain Java over BigDecimal — no database, no container, no framework context required to test it.
  • No version lock-in on the core. A host can adopt the pricing engine without inheriting its Boot version, or use the core inside an existing app that already has its own.
  • Swapping infrastructure is a bean, not a fork. 19 in-memory implementations and 17 JDBC implementations sit behind the same interfaces.

The rule that decides everything

Ask of any capability: does a library owe this, or does a service?

  • The library owns billing facts and billing decisions — metering, rating, audit, the payment state machine, the dunning ladder, tax computation, gapless numbering, append-only ledgers.
  • The host owns identity, the three timers, message transport, and live credentials.

A library that opened its own threads or scheduled its own polls would be starting work it does not own. So it does not — and the docs say so rather than implying otherwise.

Money correctness

The guarantees, and the bugs behind them

Each of these was a real defect found by writing the failing test first, not a design intent stated up front.

Allocation never loses a penny

Hamilton–Hare largest-remainder splits the remainder across line items so the parts always sum to the whole. Rounding is HALF_EVEN throughout, and BigDecimal never degrades to double on the rating path.

Wallets cannot be overdrawn or double-spent

The ledger is append-only and enforced by database triggers, not convention. Corrections are reversals — never edits. A drawdown is atomic, and cross-currency spend is refused outright.

Invoice numbers are gapless and unique

Allocated at finalization inside a transaction, using SELECT … FOR UPDATE. The first concurrency test exposed that autocommit released the row lock before the update — 16 threads produced 4 distinct numbers. Fixed with an explicit transaction.

Two tenants can never share a series

The in-memory allocator originally keyed by string concatenation with a separator. A control character in a tenant or customer id could forge another tenant's key and hand out its invoice number. Now keyed structurally — and mutation-tested to prove it.

Tenant isolation is structural, not per-query diligence. Every repository query is keyed on tenant_id at the interface boundary, so a caller cannot construct an unscoped lookup. One audit lookup was the exception — a single-item read that omitted the predicate because the id happened to be a primary key. It now takes the tenant explicitly, like every sibling query.
The outbox, stated honestly

What is guaranteed, and what is not

Guaranteed by the library

  • The event row is written in the same transaction as the state change it describes.
  • Once that transaction commits, the event cannot be lost from the database.
  • Undelivered events are retrievable by topic for operator replay.
  • Attempts are never deleted — a failure is evidence, not garbage.

Left to your host

  • Polling findDue and publishing to a broker — no dispatcher is started.
  • Writing outcomes back via recordDelivery.
  • Retry budget, dead-lettering, and alerting on exhaustion.
The documentation was corrected to match. It previously claimed a committed change "can never go unannounced." That is not true, and it is not true by design — an event that exhausts its retries sits in the table, and only a dispatcher would have told anyone. The wording now says what is actually true: a committed event cannot be lost from the database. Wiring a dispatcher is a deliberate host decision, and the docs now say that instead of implying the work is already done.

Not just green — earned

Regressions are pinned by the test that first exposed them.

  1. Renewals silently vanished

    Event ids were built from a constant sequence number, so every renewal after the first collided with one already in the outbox — identical payload, silently dropped.

  2. Duplicate invoice numbers

    A row lock released before the counter update. The concurrency test reported 16 threads producing 4 distinct numbers.

  3. Cross-tenant series collision

    A separator-based composite key could be forged. Verified by reverting the fix and watching the test fail with expected: 1L but was: 2L.

Current limits

What it does not do yet

Stated plainly, because a gap discovered during integration costs far more than one disclosed up front.

Absent by design

  • Outbox delivery. Write side complete; the poll-and-publish loop is the host's.
  • Marketplace provider adapters. Record shape and response interpretation are done; the HTTP call is transport, so it belongs to the host. Worth separate optional modules if ever needed.
  • Authentication and RBAC. TenantResolver is the seam. Identity is not a library's business.

Genuinely open

  • Rate limiting and quotas — now closed, but not by this document. AdmissionController (token bucket + concurrency ceiling, 429/503 with Retry-After) and the optional Redis adapter sharing a quota across nodes. The parity report now marks C5 PARITY; this walkthrough predates it.
  • Load shedding and SLO reporting. Shedding is present; p99 reporting and a correctness SLI are not, so C6 stays PARTIAL.
  • Identifier validation. TenantId and CustomerId reject only null and blank. Harmless now that keying is structural; still worth tightening deliberately.
The verification posture is the thing to inherit. Structural guards assert that every starter service is reachable as a bean and that no declared capability is left unused — so a class that compiles, is covered by tests, and cannot be obtained by any application fails the build rather than shipping silently.
